# 《声浪竞速》游戏策划案

> 基于灵矽（Linx XRobot）实时语音能力的纯语音操控竞速游戏
> 版本：v1.0 草案 · 2026-10-23

---

## 1. 概述

**一句话定位**：只用声音驾驶载具闯关的轻竞速游戏——音量控制油门，音高控制升降，气息管理决定成败。

**平台契合点**：灵矽客户端提供 WebSocket + Opus、16kHz 单声道、**60ms 帧**的实时全双工语音链路，配合 `listen_state` 三态机，可精确判定"玩家正在发声/发声结束"的时机，这是"发声即操作"类玩法成立的技术前提。

**目标平台**：PC（浏览器 + 桌面客户端优先），后续可移植至灵矽 C++ SDK 支持的 Linux/macOS 及硬件玩偶形态。

---

## 2. 核心玩法

### 2.1 基础操作映射

| 玩家动作 | 游戏语义 | 判定方式 |
|---|---|---|
| 持续发声（音量越大） | 油门/上升动力 | 实时 RMS 音量 → 推力 |
| 音高变化 | 载具升降/俯仰 | 基频检测（待验证：简易版可只用音量，音高作进阶） |
| 完全静音 | 滑行/下坠 | VAD 静默判定 |
| 短促停顿后爆发 | 漂移/冲刺 | 静默 200ms 后 500ms 内检测到音量跃升 |

### 2.2 单局结构（30-90 秒）

1. **起步**：3 秒倒计时，载具静止滑行
2. **主体赛段**：穿越障碍环、窄门、加速带；撞障碍损失速度不致死
3. **静音隧道**：强制静音滑行 3-5 秒，发声即减速——制造"憋气"张力
4. **终点冲刺**：计时结算，按毫秒差排名

### 2.3 模式

- **计时挑战**：单人刷榜，每日赛道轮换
- **双人对决**：同屏分轨，两条赛道镜像，实时血量条对拼（简化方案：双方轮流发声；进阶：声源分离）
- **无尽模式**：程序生成赛道，速度随时间提升

### 2.4 难度曲线

- 前 5 关：只需音量控制，建立"喊得越猛跑得越快"的正反馈
- 6-15 关：引入静音隧道，教学气息管理
- 16 关后：组合机制（隧道中穿插加速带）

## 3. AI 的角色

| AI 角色 | 职责 | 边界 |
|---|---|---|
| **实时解说员** | 播报走位、失误、破纪录、名场面 | 只解说，不干预物理；解说文本由服务端事件触发，TTS 流式播放 |
| **赛后教练** | 复盘气息稳定性、哪一段音量控制失衡 | 基于本局音频特征统计，不做跨局人格化承诺 |
| **AI 对手**（可选） | 单人模式下的"幽灵车"——复刻好友最佳录音 | 幽灵只是回放，非实时推理 |

**设计原则**：赛道物理与判定全部在客户端/服务端程序内完成，AI 只负责"表达"，不掌握任何胜负判定权。

## 4. 竞品对比

| 维度 | 声浪竞速 | 音游（Cytus / 太鼓） | 体感/手柄竞速 | 语音控制 App（小工具类） |
|---|---|---|---|---|
| 输入方式 | 纯语音 | 触屏/按键 | 专用硬件 | 语音指令 |
| 硬件门槛 | 麦克风 | 触屏设备 | 体感设备 | 麦克风 |
| 核心乐趣 | 气息管理 + 正反馈 | 节奏精度 | 沉浸操控 | 工具效率 |
| 单局时长 | 30-90 秒 | 2-4 分钟 | 3-10 分钟 | — |
| 传播属性 | 主播大喊名场面，天然短视频素材 | 录屏/手元 | 需设备铺垫 | 无 |
| 主要壁垒 | 关卡设计 + 赛事运营 | 曲库授权 | 硬件生态 | — |
| 主要弱点 | 长时间玩费嗓子；公共场合受限 | 需要乐感 | 门槛高 | 无游戏深度 |

**差异化结论**：以"最低硬件门槛 + 最强情绪释放"切入，用直播裂变弥补品类新鲜度不足；必须内置"每 3 局强制休息"的护嗓设计，避免健康争议（待验证假设：连续发声 10 分钟以上不适感显著）。

## 5. 商业价值评估

### 5.1 变现模式

| 模式 | 说明 | 优先级 |
|---|---|---|
| 赛道/角色 DLC | 主题赛道包、载具皮肤 | 高 |
| 解说声线包 | AI 解说员音色/风格（燃系、毒舌、温柔） | 高（复用 TTS 音色能力） |
| 锦标赛通行证 | 周赛 + 排行榜 + 赛季皮肤 | 中 |
| 线下大屏授权 | 商场/展会/网吧互动装置 | 中（待验证需求） |

### 5.2 获客假设

- 主播"破防大喊"片段天然适合短视频平台，假设单条爆款视频获客成本显著低于买量（**待验证假设**）
- 双人模式具备"拉好友同屏对决"的社交钩子

### 5.3 成本结构

- 主要成本为实时语音链路带宽与 ASR/TTS 调用；本地特征计算（音量/VAD）放客户端，仅解说 TTS 走服务端，可压低单位成本
- 假设单用户月均推理成本可控在个位数分币级，DLC 毛利为主要利润来源（**待验证**）

### 5.4 风险

- **平台依赖风险**：灵矽语音链路 SLA 直接影响体验，需合同级确认
- **健康/扰民风险**：需默认降噪与灵敏度校准，避免诱导嘶吼
- **新鲜感衰退**：需赛季制内容更新节奏支撑

## 6. 工程考量

### 6.1 延迟预算（关键指标）

| 环节 | 预算 | 说明 |
|---|---|---|
| 麦克风采集 | ~20ms | 系统缓冲 |
| 上行传输 | ~20-40ms | Opus 60ms 帧 |
| 服务端特征计算 | <10ms | 若做服务端权威 |
| 下行状态同步 | ~20-60ms | 双人模式才需要 |
| **端到端合计** | **<150ms 可玩；>200ms 明显不适** | 数值为待验证假设，需真机实测 |

单人模式可将音量判定完全放在本地（Web Audio API），零网络延迟；双人对决才必须服务端权威。

### 6.2 音频处理

- **VAD + 降噪**：过滤电视声、旁人说话；灵矽链路若内置则复用，否则本地 Web Audio 处理
- **个人基线校准**：首次进入录 3 秒环境音 + 试唱，建立个人音量阈值（不同麦克风增益差异巨大）
- **灵敏度滑杆**：实时可调，默认值随校准结果设定

### 6.3 架构选型

```
[客户端] 麦克风 → Web Audio 特征(音量/VAD) → 本地物理模拟 → 渲染
                    ↓ 仅事件/比分
[服务端] 房间/匹配/排行榜/解说TTS触发 → 灵矽 WS 链路 → TTS 流式播放
```

- 物理在客户端保证零延迟；服务端仅在双人/排行榜场景做权威校验
- 防作弊：成绩上报附带音频特征摘要，服务端做合理性校验（待验证有效性）

### 6.4 降级与容错

- 语音链路断开 → 本地物理继续，仅丢失解说；5 秒内重连恢复
- 解说 TTS 超时 → 跳过本条，不影响游戏
- 环境音嘈杂误触 → 灵敏度滑杆 + 快捷键盘备用操作（开发期调试必备）

### 6.5 里程碑

| 阶段 | 周期 | 产出 |
|---|---|---|
| M1 原型 | 2 周 | 单关 + 本地音量控制 + 占位音效，验证延迟与手感 |
| M2 可玩版 | 2 周 | 10 关 + 校准流程 + 接入灵矽 TTS 解说 |
| M3 上线版 | 2 周 | 排行榜 + DLC 框架 + 双人对决（轮流方案） |
| 后续 | — | 声源分离双人、无尽模式、硬件玩偶形态 |

## 7. 待验证假设清单

1. 60ms 帧链路下，端到端语音操控延迟能否稳定 <150ms
2. 连续发声 10 分钟的用户不适率与流失关系
3. 直播裂变获客成本是否显著低于买量
4. 双人声源分离在普通 PC 麦克风条件下的可行率
5. 解说 TTS 单位成本能否压至毛利可接受区间
